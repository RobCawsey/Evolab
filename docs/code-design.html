The code, explained from nothing

How this codebase is put together and why it is put together that way. It assumes you have never seen the project, never written a genetic algorithm, and have not decided yet whether you care. Every type, every module and every rule is introduced before it is used.

01

The shape of the whole thing

Evolab is a program that invents ways for a two-legged robot to walk. It does not do this by being told how to walk. It generates a few dozen random attempts, scores each one by simulating it, breeds the better ones together, and repeats. After thirty rounds of that, something walks.

All of it runs in a web browser. There is an optional server, but the interesting part — the physics, the search, the drawing — happens in the tab.

The code is in four layers. The single most important thing to understand before reading any file is that dependencies only ever point one way: down the list below, never up it.

Why upside down?

In a typical application the "core" is a database and everything else depends on it. Here the core is arithmetic: given eleven numbers, what angles should the joints be at? Given a trial result, what is it worth? Given a population, which pairs breed?

None of that needs a physics engine, a canvas, or a network. Keeping it in a layer that cannot reach those things has three consequences that show up constantly:

  • The entire genetic algorithm runs under Node in milliseconds, against a fake evaluator. Tests do not need a browser or a physics world.
  • The same code runs on the main thread, inside four Web Workers, and in a command-line script, without a single conditional.
  • When something breaks you can nearly always tell which layer it broke in, because the layers cannot reach into each other.
The one-sentence version The core computes, the middle simulates, the app displays, the server remembers — and each only knows about the ones below it.

02

The dependency rules

Four rules govern what may import what. They are written down in CLAUDE.md as project invariants, and breaking one is treated as a bug even when the program still runs. Here they are with the reasoning, because a rule you do not understand is a rule you will route around.

Rule 1 — Physics steps at a fixed rate

The simulation always advances in increments of exactly 1/240 of a second, never by however long the last animation frame happened to take. A physics engine given variable time steps produces different results on a fast machine than a slow one, and every reproducibility guarantee in the project collapses.

Rule 2 — Randomness is seeded, always

There is no Math.random() anywhere in packages/. Random numbers come from an Rng object that is created from a seed and passed explicitly as a function argument. Give it the same seed and it produces the same sequence for ever.

This is what makes it possible to say "seed 4417, thirty generations, fitness 6.4598" and have that be true on any machine — which in turn is what makes an automated test able to catch an accidental change to the algorithm.

Rule 3 — The core stays pure

packages/evolution may not import the physics engine, touch the DOM, read a file, or set a timer. If a function in there needs to simulate something, it takes a function that does the simulating as an argument. That pattern appears three times in the codebase and section 8 explains it properly.

Rule 4 — The physics layer owns the physics

packages/sim is the only place that imports Rapier, the physics engine. It turns a body plan into a world, steps that world, and hands back plain numbers. It does not draw anything, and it does not know what a genome is.

What breaking these actually costs These are not stylistic preferences. A single Math.random() in the core would make runs unreproducible, silently invalidate the regression test that guards the whole algorithm, and make every bug in the search unrepeatable. The rules are cheap to keep and expensive to restore.

The vocabulary

Nine types carry almost everything. Learn these and the rest of the codebase reads as plumbing between them. They are introduced here in the order data flows through them.

The distinction that matters most TrialResult holds both quality (distance, upright, effort — the things score() reads) and behaviour (stride length, duty factor — which score() deliberately ignores). 04

The pure core — packages/evolution

Nine files, no dependencies at all — not one line of it imports anything outside itself. This is where the program's actual ideas live.

rng.ts — repeatable randomness

A small class implementing xoshiro128**, a well-known pseudo-random generator. "Pseudo-random" means the numbers look random but are entirely determined by the starting seed. Create two with the same seed and they produce identical sequences for ever.

It is the only class in the package, because it is the only thing with genuine state: each number it produces changes what the next one will be. Everything else is a plain function.

The code

export class Rng {
  readonly seed: number;
  private readonly s: Uint32Array;          // four 32-bit words — the entire state

  constructor(seed: number) {
    this.seed = seed;
    const mix = splitmix32(seed);           // spread one seed into four words
    this.s = new Uint32Array([mix(), mix(), mix(), mix()]);
    // A four-zero state is a fixed point of the generator: it would return zero for ever.
    // Unreachable from splitmix32 in practice, but cheap to rule out.
    if (this.s.every((w) => w === 0)) this.s[0] = 1;
  }

  u32(): number {                            // one raw 32-bit number
    const s = this.s;
    const result = (Math.imul(rotl(Math.imul(s[0 + 1]!, 5), 7), 9) >>> 0);
    const t = (s[1]! << 9) >>> 0;
    // shuffle the four words into each other — this is the whole algorithm
    s[2] = (s[2]! ^ s[0]!) >>> 0;
    s[3] = (s[3]! ^ s[1]!) >>> 0;
    s[1] = (s[1]! ^ s[2]!) >>> 0;
    s[0] = (s[0]! ^ s[3]!) >>> 0;
    s[2] = (s[2]! ^ t) >>> 0;
    s[3] = rotl(s[3]!, 11) >>> 0;
    return result;
  }

  float():  number { return this.u32() / 4294967296; }   // [0, 1)
  range(lo, hi) { return lo + this.float() * (hi - lo); }
  int(n)       { return Math.floor(this.float() * n); }
}

Three things in there are worth pulling out, because each is a general lesson rather than a detail about random numbers.

>>> 0 everywhere. JavaScript has no integer type — every number is a 64-bit float. Bit operations silently convert to a signed 32-bit integer, so a result with the top bit set comes back negative. The unsigned right-shift by zero forces it back to unsigned. Miss one and the generator still produces numbers, still looks random, and no longer matches any other implementation of xoshiro128** on earth.

Math.imul rather than *. Multiplying two large 32-bit values as floats loses the low bits to rounding. Math.imul does a true 32-bit integer multiply and keeps the bits that matter.

The zero-state guard. All four words being zero is a state the generator can never escape from — it would return zero for ever. It is unreachable in practice, and the check is one line. This is a recurring shape in this codebase: when the impossible case is catastrophic and the guard is trivial, write the guard.

Why a class here, and nowhere else Rng is the only class in the package because it is the only thing with genuine state — each call to u32() changes what the next one returns. Everything else is a plain function that maps inputs to outputs. The project's convention is "no classes unless there is state with a lifecycle", and this is one of exactly two things that qualifies (the other is Sim, which wraps a physics world that must be explicitly freed).
The comment in the real file worth knowing about You might expect constructor(readonly seed: number) — TypeScript's shorthand for "take this parameter and also store it as a field". It is not used, and that is deliberate: that syntax emits code rather than only removing types, and the command-line scripts run TypeScript through Node's --experimental-strip-types, which only erases. The same rule rules out enum, namespaces and decorators across the whole project.

controller.ts — turning numbers into movement

The robot has six joints: a hip, knee and ankle on each leg. Each one is driven like a pendulum — it swings back and forth on a repeating cycle. Three numbers describe such a swing:

  • amplitude — how far it swings
  • phase — where in the cycle it starts, so the two legs can be offset
  • centre — the angle it swings around

Three joint kinds × three numbers = nine, plus an overall frequency (how fast the cycle runs) and a balance gain (how strongly the robot leans back when it feels itself pitching forward). Eleven numbers, and that is the entire vocabulary available to the robot.

The left and right legs use the same nine numbers, driven half a cycle apart. That is why a robot cannot learn to limp, and why it cannot learn to turn.

// the whole controller interface, in three functions
decodeGenome(genes: Genome): GaitParams      // 11 raw numbers → things with units
encodeGenome(params: GaitParams): Genome     // and back, for hand-tuned gaits
gaitTargets(morph, params, time, state, out) // → what angle each joint should be at now

gaitTargets is called sixty times per simulated second and writes into a map the caller supplies, rather than allocating a new one. It runs tens of millions of times in a long study, so it is one of the very few places in the codebase written for speed.

The state argument is ControlState — just { pitch, pitchRate }, the robot's sense of which way up it is. That is the only thing the controller knows about the world. It cannot see the ground, an obstacle, or where it is going. Understanding that one fact explains most of the project's later findings.

The whole controller, in fourteen lines

export function gaitTargets(
  morph: Morphology,
  params: GaitParams,
  t: number,                                // simulated seconds since the trial began
  state: ControlState = STILL,              // { pitch, pitchRate } — all it can sense
  out?: Map<string, number>,                // written into, to avoid allocating
): Map<string, number> {
  const targets = out ?? new Map<string, number>();
  targets.clear();

  const cyclePhase = 2 * Math.PI * params.frequency * t;

  // One number, shared by both hips: how far forward the torso is predicted to be, times
  // the gain. Driving the thighs forward against a forward lean pushes the torso back
  // upright by reaction — the hip balance strategy, in one line.
  const correction = params.balanceGain * (state.pitch + PITCH_LEAD * state.pitchRate);

  for (const joint of morph.joints) {
    const g = params[joint.kind];             // the hip / knee / ankle triple
    let angle = g.centre + g.amplitude * Math.sin(cyclePhase + g.phase + SIDE_PHASE[joint.side]);
    if (joint.kind === 'hip') angle += correction;
    targets.set(joint.id, clamp(angle, joint.limits[0], joint.limits[1]));
  }

  return targets;
}

That is the entire brain of the robot. Everything it will ever do is in that Math.sin.

Read the angle line first. centre + amplitude × sin(…) is a joint swinging back and forth: centre is the middle of the swing, amplitude is how far either side it goes, and the argument to sin decides where in the swing it is right now. That argument has three parts added together:

  • cyclePhase — the clock. It advances steadily with time, at a rate set by the evolved frequency gene.
  • g.phase — an evolved offset per joint kind. This is what lets the knee lag behind the hip, which is the difference between walking and flailing.
  • SIDE_PHASE[joint.side] — a constant, 0 for the left leg and π for the right. Half a cycle apart. Not evolved.

That last one is the single most consequential line in the project. The two legs are driven by the same three numbers, offset by exactly half a cycle. That is why the robot cannot limp, cannot favour one leg, and — because there is no gene that could ever make one leg step differently from the other — cannot turn. When the task suite later needed a slalom course and could not have one, this constant is the reason.

The one closed loop Everything above is open-loop: it is a function of the clock and nothing else. The robot would do exactly the same thing on a slope, on ice, or in mid-air. The single exception is correction, which reads the torso's pitch and pushes the hips against it.

Notice PITCH_LEAD * state.pitchRate. Feeding back the angle alone always lags — by the time the error is big enough to correct, the robot already has the momentum to keep going, so it overshoots and oscillates. Adding a fraction of the rate of change is a first-order prediction of where the torso will be in 0.12 seconds, and damps the response. It is a fixed constant rather than a twelfth gene, deliberately: one tunable number is the whole point of choosing this controller.

Genome in, parameters out

A genome is eleven numbers between 0 and 1. They only become meaningful by being stretched into real ranges:

// evolution never sees these ranges. It works entirely in [0, 1].
const GENE_RANGES = [
  [0.4, 2.6],      // frequency, Hz
  [0.0, 3.0],      // balance gain
  ... nine more, three per joint kind
];

export function decodeGenome(genome: Genome): GaitParams {
  return {
    frequency:   lerp(genome[0]!, 0),
    balanceGain: lerp(genome[1]!, 1),
    hip:   { amplitude: lerp(genome[2]!, 2), phase: lerp(genome[3]!, 3), centre: lerp(genome[4]!, 4) },
    knee:  { amplitude: lerp(genome[5]!, 5), phase: lerp(genome[6]!, 6), centre: lerp(genome[7]!, 7) },
    ankle: { amplitude: lerp(genome[8]!, 8), phase: lerp(genome[9]!, 9), centre: lerp(genome[10]!, 10) },
  };
}
Why unit space matters Because every gene lives in [0, 1], the crossover and mutation operators never need to know what a gene means. Mutating a frequency and mutating an angle are the same operation on the same scale. That is what keeps operators.ts completely free of any controller knowledge — it is a general-purpose genetic algorithm that happens to be pointed at a robot.

morphology.ts — building a body

buildBiped(spec) takes editable measurements and produces a Morphology: a list of boxes with positions, sizes and densities, and a list of joints with the exact point on each box where they attach.

Because the geometry is derived rather than stored, the chain always closes: the ankle is always at the bottom of the shank, and the feet always rest exactly on ground level. You cannot produce an incoherent robot by editing a slider.

The file also computes bodyStats — mass, standing height, balance margin, hip load — and validateBody, which explains why a body will not work rather than only refusing it.

The three joint numbers, properly

Nine of the eleven genes are three numbers repeated for each of the three joint kinds: amplitude, phase and centre. These are the numbers on the sliders, the numbers the search is actually searching, and the ones that are hardest to picture. This section is about nothing else.

Start from what a joint is doing. Each joint has one angle, and that angle changes over time. If you plotted it you would get a wave — up, down, up, down, once per stride. The three numbers are simply three different ways of describing that wave.

Centre — where the joint sits

The easy one. It is the angle the joint holds on average, in radians, measured from the robot's rest pose. If amplitude were zero, the joint would simply stay locked at this angle.

A knee with a centre of -0.35 stands with its knee permanently bent about 20°. A hip with a centre of +0.1 holds its thigh slightly forward all the time. Changing the centre changes the robot's posture.

Amplitude — how big the movement is

Also easy. How far the joint swings either side of its centre, again in radians. Zero means the joint does not move at all. Larger values mean bigger, sweepier motions.

Amplitude cannot be negative, and the reason is worth noticing: swinging by -0.4 would be identical to swinging by +0.4 starting half a cycle later, which is something phase can already express. Allowing both would mean two different genomes producing exactly the same robot, and the search would waste its time exploring duplicates.

Phase — the one that is genuinely hard

The short answer Phase is not an angle the joint moves to. It is a time offset — it says when in the stride this joint does its thing, relative to the clock. It is measured in radians only because that is the unit the sine function wants; it means "how far around the cycle to start".

Everything else is measured in "how far". Phase is measured in "how late". That is why it feels unlike the other two.

A full cycle is 2π, about 6.28. So:

  • phase = 0 — start at the beginning of the cycle
  • phase = π/2 (1.57) — start a quarter of the way through
  • phase = π (3.14) — start halfway through, i.e. exactly out of step
  • phase = 2π (6.28) — a whole cycle late, which is the same as not late at all

That last point is the strange and important one: phase wraps around. The range in this project is [0, 2π], and the two ends of that range mean the same thing. A genome with a hip phase of 6.2 and one with a hip phase of 0.08 produce almost identical robots, despite sitting at opposite ends of the gene's range.

What that costs the search Crossover and mutation treat every gene as a plain number on a line, so they have no idea that the two ends of a phase gene are neighbours. A parent at 0.05 and a parent at 6.2 are nearly identical robots, but blending them produces a child at about 3.1 — which is half a cycle out from both parents and typically falls over. This is a real, known limitation of encoding a circular quantity as a linear gene, and the project accepts it: the search works around it by finding a phase relationship that works and then staying near it.

Why phase is what makes it a walk

Amplitude and centre decide what a leg looks like. Phase decides whether it walks.

Consider what a real leg does. On the way forward, the knee bends so the foot clears the ground. On the way back, the knee straightens so the leg can take weight. The knee is doing the same repetitive motion as the hip — just at a different moment in the stride.

If the hip and knee are given the same phase, they swing together: the knee bends exactly when the leg swings forward and straightens exactly when it swings back, which is roughly the opposite of useful. Offset them correctly and you get a step.

And the other leg

/** Left and right run half a cycle apart. This is what makes it a gait and not a hop. */
const SIDE_PHASE = { L: 0, R: Math.PI } as const;

// inside gaitTargets, for every joint:
let angle = g.centre + g.amplitude * Math.sin(cyclePhase + g.phase + SIDE_PHASE[joint.side]);

There are two phase offsets added together, and they do different jobs:

  • g.phase — evolved, one per joint kind. Sets the hip-to-knee-to-ankle timing within a leg. This is what the search is discovering.
  • SIDE_PHASE[side] — a constant, 0 for the left leg and π for the right. Puts the two legs exactly half a cycle apart, so that one is planted while the other swings.

Because the second is a constant rather than a gene, the two legs can never do anything different from each other. That is why the robot cannot limp, cannot favour an injured side, and cannot turn — and it is why the task suite has six tasks rather than the eight the design originally called for.

The actual ranges, and why they differ

export const GAIT_RANGES = {
  frequency:   [0.5, 3.0],                 // cycles per second
  balanceGain: [-2, 2],
  hip:   { amplitude: [0, 0.8], phase: [0, 2 * Math.PI], centre: [-0.5,  0.5] },
  knee:  { amplitude: [0, 0.9], phase: [0, 2 * Math.PI], centre: [-0.8,  0.1] },
  ankle: { amplitude: [0, 0.5], phase: [0, 2 * Math.PI], centre: [-0.4,  0.4] },
} as const;

All three phases share the full [0, 2π] range, because "any moment in the cycle" is meaningful for every joint. The other two are shaped by anatomy:

  • The knee's centre runs [-0.8, 0.1] — almost entirely negative. A knee bends one way. Allowing it to sit bent forwards would be describing a robot that cannot exist.
  • The ankle's amplitude is capped at 0.5, lower than the hip and knee. An ankle has the least range of the three and pushing it hard mostly wastes effort.
  • The hip's centre is symmetric, [-0.5, 0.5]. A thigh swings equally well forwards and backwards.

These are the gene ranges — what evolution may propose. Separately, the body itself has hard joint limits which the physics enforces, and which gaitTargets clamps every target against before handing it to a motor:

limits: {
  hip:   [-50 * DEG,   90 * DEG],          // −50° behind, 90° in front
  knee:  [-132 * DEG,   8 * DEG],          // bends a long way one way, barely the other
  ankle: [-35 * DEG,   25 * DEG],
}
Two different kinds of limit Gene ranges say what evolution is allowed to ask for. Joint limits say what the body can physically do. They are separate on purpose: the body is editable in the interface, so a shorter robot with tighter joints must still be drivable by the same eleven-gene genome. gaitTargets reconciles them with a clamp on the last line, so a gait evolved for one body never asks a different body to bend somewhere it cannot.

A worked example

Here is the starting gait the app opens with — deliberately upright and rhythmic, and deliberately not able to walk:

export function defaultGait(): GaitParams {
  return {
    frequency:   1.4,                                       // 1.4 strides per second
    balanceGain: 0.5,
    hip:   { amplitude: 0.4, phase: 0,   centre:  0.1  },
    knee:  { amplitude: 0.5, phase: 2.2, centre: -0.35 },
    ankle: { amplitude: 0.2, phase: 3.6, centre:  0    },
  };
}

Read as English: a stride takes about 0.7 seconds. The thigh swings 23° either side of a point slightly forward of vertical, starting at the top of the cycle. The knee swings 29° either side of a 20°-bent posture, but does so 2.2 radians — about 35% of a cycle — later than the hip. The ankle makes a small 11° motion, later again.

The hip phase is 0, and that is not a coincidence: with only relative timing mattering, one joint can always be treated as the reference and the others described against it. Evolution does not know that and will happily discover a hip phase of 4.1 with everything else shifted to match — producing an identical robot from a completely different-looking genome. This is another reason two genomes can look nothing alike and behave the same way.

If you take one thing from this section Amplitude and centre describe a shape. Phase describes timing. Getting a robot to stand is a matter of centres; getting it to move is a matter of amplitudes; getting it to walk is almost entirely a matter of phases. That is also the order of difficulty, and it is why the fitness curve tends to climb in three distinct steps.

operators.ts — the genetic machinery

Four small functions, each a standard technique with a fixed, named constant:

FunctionWhat it doesSetting
randomGenomeEleven random numbers. This is generation zero — nobody designs it.—
tournamentPicks three individuals at random and returns the best. Repeat to pick each parent.size 3
sbxSimulated binary crossover. Blends two parent genomes into two children, usually landing near the parents and occasionally further out.η = 15
mutatePolynomial mutation. Nudges individual genes by a small random amount.η = 20
diversityMean distance between all genome pairs — how different the population still is.—
Why a tournament rather than "pick the best two" Because picking three at random and keeping the winner means a weak genome can still get lucky. Always breeding the very best would collapse the population onto one answer within a handful of generations, and the search would stop finding anything new.

Selection: a three-way tournament

export function tournament(
  fitness: readonly number[],
  size: number,                              // 3
  rng: Rng,
  drawn?: number[],                          // optional: record who was drawn, for the stepper
): number {
  let best = rng.int(fitness.length);       // pick someone at random
  drawn?.push(best);
  for (let i = 1; i < size; i++) {
    const challenger = rng.int(fitness.length);
    drawn?.push(challenger);
    if (fitness[challenger]! > fitness[best]!) best = challenger;
  }
  return best;                              // an index, not an individual
}

Eight lines, and it is the entire mechanism by which the population improves. Pick three at random, keep the best. Do it twice to get two parents.

The drawn parameter is worth noticing. It is undefined during a normal run, so the function allocates nothing and records nothing. The teaching stepper passes an array and gets back exactly which three individuals were drawn, so it can show the tournament happening. Instrumentation that costs nothing when it is off appears three times in this codebase — here, in crossover's blended, and in mutation's record.

Crossover: blending two parents

for (let i = 0; i < n; i++) {
  const a = p1[i]!, b = p2[i]!;

  if (rng.float() > probability) {          // 10% of genes are copied, not blended
    c1[i] = a; c2[i] = b;
    continue;
  }

  const u = rng.float();
  const beta = u <= 0.5
    ? Math.pow(2 * u, 1 / (eta + 1))
    : Math.pow(1 / (2 * (1 - u)), 1 / (eta + 1));

  c1[i] = clamp01(0.5 * ((1 + beta) * a + (1 - beta) * b));
  c2[i] = clamp01(0.5 * ((1 - beta) * a + (1 + beta) * b));
}

This is simulated binary crossover. Ignore the exponent for a moment and look at the last two lines: they are a weighted average of the two parents, with the weights decided by beta. When beta is 1 the children are exact copies of the parents; when it is near 0 both children land halfway between them; when it exceeds 1 the children land outside the parents, further apart than they were.

The eta constant — 15 here — controls how often that last case happens. Higher values keep children close to their parents; lower values scatter them. It is the knob between refining what you have and looking somewhere new.

island.ts — one generation

An island is a population plus the settings it runs under plus its own random generator. The name comes from the island model of evolution: several populations evolving separately and occasionally exchanging a few members.

One generation goes: score everyone, sort, keep the best two unchanged, then repeatedly pick two parents and breed them until the population is full again.

Scoring only what needs scoring

export function evaluatePending(island: Island, evaluate: Evaluator): number {
  const cfg = island.config;
  let evaluations = 0;
  for (const ind of island.population) {
    if (ind.result !== null) continue;      // an elite — already scored, do not re-run
    const result = evaluate(ind.genes, cfg.trialSeed);
    ind.result  = result;
    ind.fitness = score(result, cfg.trialSeconds, cfg.objective).total;
    evaluations++;
  }
  return evaluations;
}

Two details carry a lot of weight here.

if (ind.result !== null) continue — an individual carrying a result has already been through a trial. The two elites copied forward from the last generation are in exactly that state, so they are not re-run. In a population of 24 with 2 elites that is 22 trials per generation rather than 24, which is roughly an 8% saving on the most expensive operation in the program.

cfg.trialSeed, not a per-generation seed. Every trial in the whole run uses the same seed, which decides the small random tilt the robot starts with.

A bug this project actually shipped The seed originally varied by generation, which sounds more rigorous — test each generation against fresh conditions. But elites are not re-evaluated, so an elite that got a favourable tilt in generation 5 carried that lucky score forward for ever while everyone around it was judged on harder draws. The reported champion was part luck and the best-fitness curve was not honestly monotonic.

The general rule, which is worth carrying anywhere: if a score survives across generations, the conditions it was scored under must not change. The cost is that a champion is tuned to one perturbation — which is precisely why the task suite later re-tests every gait across five unseen seeds and reports the median.

Breeding, one pair at a time

for (let i = 0; i < cfg.elites && i < ranked.length; i++) {

let pair = 0;
while (next.length < cfg.size) {

  const ib = tournament(fitnesses, cfg.tournamentSize, rng);      //  │ select
  const a = island.population[ia]!, b = island.population[ib]!;   // ─┘

  const [c1, c2] = sbx(a.genes, b.genes, rng, SBX_ETA, cfg.crossoverProbability);  // cross

    // The population can fill on the first child, in which case the second is discarded
    // *before* being mutated and consumes no randomness. Preserving that is part of
    // preserving the draw order.
    if (next.length >= cfg.size) break;
    mutate(child, rng, mutationRate, MUTATION_ETA);                 // mutate
    next.push({ genes: child, fitness: 0, result: null });
  }
  pair++;
}

Notice that select → cross → mutate happens completely for one pair before the next pair begins. It would be tidier to gather all the selections, then do all the crossovers, then all the mutations. It would also be a different program.

The reason is the shared rng. Every call to tournament, sbx and mutate pulls numbers from the same sequence, in order. Reordering the calls reorders the draws, so every genome downstream is different. Both versions are valid genetic algorithms; they are simply not the same genetic algorithm.

The break in the middle is subtler still. With an odd number of slots left, the second child is thrown away — and it is thrown away before mutate is called, so it never consumes any random numbers. Move that break below the mutation and every subsequent draw shifts.

How you find out you broke it npm run evolve stops printing 6.4598. That is the entire safety net for this function, and it is why the number is pinned in a test rather than left as a note.
The trap in this file Grouping the phases for tidiness would silently invalidate every stored gait in the project and change the pinned regression number. If you touch breed(), the way you find out you were wrong is that npm run evolve stops printing 6.4598.

The generation is a JavaScript generator

generation() is written with function*, meaning it can pause and hand control back to its caller at defined points. Normal runs drain it as fast as possible and never look at the pauses:

export function stepGeneration(island, evaluate) {
  const it = generation(island, evaluate);
  let step = it.next();
  while (!step.done) step = it.next();   // drain, ignoring every stage
  return step.value;
}

But the teaching screen — the "stepper" — advances it one pause at a time and draws what it finds. This means the screen that explains the algorithm is running the algorithm, not an illustration of it. A test asserts that a traced run and an untraced run produce identical results, because the moment that stops being true the teaching screen becomes a lie.

One generation, two speeds

export function* generation(
  island: Island,
  evaluate: Evaluator,
  opts: GenerationOptions = {},
): Generator<Stage, GenerationSummary> {
  const trace = opts.trace ?? false;

  if (trace) yield { stage: 'population', generation: island.generation, ... };

  const evaluations = evaluatePending(island, evaluate);
  const { ranked, fitnesses, summary } = rankPopulation(island, evaluations);

  if (trace) yield { stage: 'evaluate', evaluations, fitnesses, ranked: order };

  yield* breed(island, ranked, fitnesses, trace);   // yields select/crossover/mutate per pair

  if (trace) yield { stage: 'replace', summary };
  return summary;
}

The function* and yield keywords make this a generator: a function that can pause, hand a value back to whoever called it, and resume where it left off.

The search drains it as fast as it can and ignores every pause. The teaching stepper advances it one pause at a time and draws whatever it finds. Same function, same random draws, same result — one code path at two speeds.

Every yield is behind if (trace), so a normal run allocates none of those objects. And the yield* in the middle delegates to breed, which is itself a generator, so the pairs stream through without generation knowing how many there will be.

Why this is the design that makes the teaching honest The alternative is a second, simplified implementation written for the screen. That version would be easier to write and would drift from the real one within a month. Instead there is one implementation, and a test asserts that a traced run and an untraced run produce identical results — so the screen cannot show something the algorithm does not do.

fitness.ts — what "good" means

Holds TrialResult (what a trial produced) and score() (what that is worth). Scoring mixes three terms in proportions given by an Objective: distance travelled, seconds spent upright, and effort spent — where effort is total joint movement, above a budget.

TrialResult lives here rather than in the physics package on purpose: it is a description of an outcome, not a piece of physics, and the core is not allowed to import the simulator anyway.

Scoring a trial

export function score(
  result: TrialResult,
  requestedDuration: number,
  objective: Objective = DEFAULT_OBJECTIVE,
): FitnessBreakdown {
  const distance = objective.distance * result.distance;
  const upright  = objective.upright  * (result.uprightTime / requestedDuration);

  // Computed via the excess so an unpenalised trial reports +0 rather than -0. Negative
  // zero is harmless arithmetically and confusing in a printed breakdown.
  const excess = Math.max(0, result.effort / objective.effortBudget - 1);
  const effort = excess === 0 ? 0 : -objective.effort * excess;

  // Clamped at zero: negative fitness makes tournament selection compare noise, and a
  // genome that walks backwards is not more interesting than one that stands still.
  const total = Math.max(0, distance + upright + effort);
  return { total, distance, upright, effort };
}

Three terms, each returned separately as well as summed. Returning the breakdown rather than just the total is what lets the interface show why a robot scored what it did, and it costs nothing.

Effort is only penalised above a budget. Below it, moving costs nothing. That shape matters: a penalty that applies from zero would make standing perfectly still the cheapest option, and the search would find that immediately.

The clamp at zero, and what it costs Negative fitnesses would make tournaments compare meaningless magnitudes, so everything below zero becomes zero. The cost is that in generation zero, where nearly every robot falls over instantly, a great many individuals have exactly the same fitness of 0 — and a tournament between three of them is a coin toss. That is not a bug; it is what "no selection pressure yet" looks like, and watching the first few generations move slowly for that reason is one of the things the teaching stepper is for.
An honest naming decision worth copying The design called for energy in joules. The physics engine's JavaScript binding does not expose the forces its motors applied, so joules cannot be measured. The field is therefore called effort and documented as "total joint travel in radians" — named for what it measures rather than for what it approximates. The same decision recurs later, where cost of transport becomes "joint travel per metre".

archive.ts — a map of what was found

The genetic algorithm answers one question: what is the best gait? The archive answers a different one: what kinds of gait are there, and how good is the best of each kind?

It is a 24 × 24 grid. Along one axis, stride length — how far the robot travels between one footfall and the next of the same foot. Up the other, duty factor — the fraction of time a foot is on the ground. Every cell holds the fittest genome that has ever behaved that way.

Observer, never input A test drains an island's archive every generation and asserts the population comes out bit-identical. Remove the archive entirely and the search is unchanged. That is what makes it an observation rather than a second algorithm.

The archive's one rule

export function archiveInsert(archive, genome, behaviour, fitness, generation = 0): boolean {
  return archivePlace(archive, archiveIndex(archive, behaviour), genome, behaviour, fitness, generation);
}

export function archivePlace(archive, index, genome, behaviour, fitness, generation = 0): boolean {
  archive.attempts++;
  if (index < 0 || index >= archive.cells.length) return false;

  const incumbent = archive.cells[index] ?? null;
  if (incumbent !== null && incumbent.fitness >= fitness) return false;   // ties lose

  // Copied. The population mutates its genomes in place between generations, and an archive
  // holding a live reference would silently rewrite its own history.
  archive.cells[index] = {
    genes: Float32Array.from(genome),
    fitness,
    behaviour: [behaviour[0], behaviour[1]],
    generation,
  };
  if (incumbent === null) archive.filled++;
  archive.improvements++;
  return true;
}

Float32Array.from(genome) is not defensive style — it is load-bearing. The population reuses and mutates its genome arrays in place between generations. An archive holding a reference rather than a copy would find its stored history quietly rewritten underneath it, and cells would report genomes that no longer match their fitness.

>= rather than > means ties lose: an equal score does not displace the incumbent. That makes the map stable to look at — a cell that stops changing has genuinely converged rather than churning between equivalent genomes every generation. It is also, unexpectedly, what makes re-publishing a run to the shared community map a no-op, because a run's own cells tie with themselves.

The split between the two functions exists because of one measured bug. archiveInsert derives the grid cell from the behaviour. That is right for a live search, and wrong for a cell read back from storage, where the stride and duty have been rounded to four decimals for the wire. A stride of 0.87499 stored as 0.8750 sits exactly on a bin boundary and re-derives one column to the right — 244 cells were sent and 243 appeared. So the index is authoritative once it exists, and both functions still share the one tie rule.

terrain.ts and tasks.ts — testing a gait

terrain.ts turns a description — flat, a ramp of so many degrees, steps of so many centimetres, seeded rough ground — into an array of ground heights sampled every two centimetres, plus a function answering "how high is the ground at this x?".

It is pure arithmetic with no physics engine in it, which is why it lives in the core rather than in the simulator: tasks.ts needs to name a terrain, and the core is not allowed to import the simulator.

tasks.ts holds six tasks as plain data — terrain, duration, any impulses, a body change, a metric name and three thresholds — plus the arithmetic that turns trial results into a scorecard. Nothing in it simulates anything; running the trials is somebody else's job, which is section 8's first pattern.

05

The physics layer — packages/sim

Four files. This layer owns Rapier — a physics engine originally written in Rust and compiled to WebAssembly so it runs in a browser — and nothing else in the project imports it.

world.ts — the Sim class

The constructor turns a Morphology into a live world: one rigid body per segment, one revolute joint per joint, collision filtering so the robot's own parts pass through each other but not through the ground, and the ground itself.

Three things about it are worth knowing before you touch it.

Motors are springs, not rigid links. Each joint is driven towards a target angle by a motor with a stiffness setting. That number needs to be far larger than a first guess suggests — around 80,000. Below roughly half that, the robot cannot hold a standing pose at all and topples in about a second, which reads exactly like a fundamental limitation of the approach and is not one. An entire debugging session went into that.

Memory must be freed by hand. Rapier objects live in WebAssembly memory, which JavaScript's garbage collector does not manage. Every Sim must have dispose() called on it, and every place that creates one in a loop does so in a finally block. A leak here is the most likely cause of a run that mysteriously slows down and then dies.

Flat ground is a special case on purpose. Terrain is built from the best shape for each profile — a ramp is one rotated slab, steps are one slab per tread — but flat ground keeps the exact collider it has always had, constructed exactly the way it always was. Moving the same offset from the body onto the collider is geometrically identical and moved the pinned regression number from 6.4598 to 5.8015.

evaluate.ts — the inner loop

One function runs one genome for one trial and returns numbers. In a long study it executes tens of thousands of times, so it is the hottest code in the project.

Foot contact is decided by geometry, not by asking the physics engine: the lowest corner of the foot box is computed and compared against the ground height beneath it, with a five-millimetre tolerance. That threshold was chosen by measurement — sweeping it from 1 mm to 10 mm changes nothing, and it collapses at 20 mm where separate steps start merging into one.

Recording is opt-in and allocates nothing when it is off. That matters: the search runs this function tens of thousands of times per study and never wants a recording, while the one genome a person is looking at wants a detailed one.

record.ts — replay data

A Recording is a set of flat typed arrays — positions, angles, contact flags — sampled sixty times a second. Flat arrays rather than an array of objects because the format is designed to be handed between threads cheaply and because it is read by three separate display surfaces.

snapshotAt(recording, frame) rebuilds a Snapshot, which means one scrubber control drives both the 2D and the 3D renderer from the same source and they cannot drift apart.

06

The application layer — apps/web

This is the only layer that knows a browser exists. It is organised into six folders by what a file is responsible for, not by what feature it belongs to.

run/state.ts — what the app is doing

One mutable object: the worker pool, the fitness history, the current champion, whether the search is running, which of the three stages the interface is in, which gait the sliders hold. There is no state-management library. For an application with one screen and one user, a plain object read by a render loop is the whole of what is needed.

workers/ — running the search off the main thread

A browser tab has one thread for JavaScript, and the same thread draws the screen. Running a search on it would freeze the interface. So the search runs in Web Workers — separate threads that share no memory and communicate only by passing messages.

Each worker holds one island: its own population, its own random generator. Every five generations each island sends its two best genomes to the next worker round a ring.

The counterintuitive result Four workers do not make generations arrive four times faster — a generation is sequential and nothing can shorten it. What four workers buy is four populations searching at once, which finds a wider variety of answers. Measured: 88 trials per second on one worker, 329 on four. Generations per second barely moves.
And the cost Multi-worker runs are not bit-reproducible. Migration is asynchronous, so a migrant arriving before generation 7 rather than after changes everything downstream. One worker is reproducible, and every guarantee the project makes is stated for the single-island case. ?workers=1 is the flag for comparing runs.

render/ — drawing

Plain canvas drawing, no framework. The render loop accumulates real elapsed time and steps the physics a whole number of fixed steps, which is what keeps rule 1 true even though frames arrive irregularly.

Two conventions here are easy to trip over. World coordinates have y pointing up; canvas coordinates have y pointing down. The flip happens in exactly one file and nowhere else. And the 2D renderer nudges the far leg sideways by a few pixels — because a strictly side-on robot has both legs in exactly the same place and looks like a pogo stick — which is the one place the drawing deliberately disagrees with the simulation.

The 3D view is optional and dynamically imported, so the 500 kB of Three.js is only downloaded if someone presses the button. The file that computes how a 2D simulation becomes a 3D scene imports nothing from Three at all, which is why it can be tested in Node without a graphics context.

net/ — talking to the server

One rule shapes this entire folder: nothing here ever throws. Every outcome — offline, timeout, a 404, a 500, an HTML error page from a proxy, or a 200 whose body is not the JSON it claimed — becomes a result value describing what happened.

type ApiResult<T> =
  | { ok: true;  data: T }
  | { ok: false; error: ApiError }

Because failure is a value rather than an exception, there is no try/catch anywhere else in the application, and no code path where a dead server matters. This was measured rather than assumed: with the server killed mid-session, thirty generations still evolved with zero unhandled rejections and no dialog — the only visible change was one amber dot in the toolbar.

Every request carries a five-second timeout, because a request that hangs produces neither an error to report nor a result to use, which is the only outcome worse than failing.

Failure as a value

async function request<T>(path: string, opts: RequestOptions = {}): Promise<ApiResult<T>> {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), TIMEOUT_MS);   // five seconds

  try {
    const response = await fetch(BASE + path, { ..., signal: controller.signal });

    // Read as text first. A proxy returning HTML with a 200 is a real thing, and `.json()`
    // on it throws in a way that would otherwise look like a network failure.
    const raw = await response.text();
    let parsed: unknown = null;
    if (raw.length > 0) {
      try { parsed = JSON.parse(raw); }
      catch {
        return response.ok
          ? { ok: false, error: clientError(CLIENT_CODES.malformed, 'The server sent something this app could not read.') }
          : { ok: false, error: normaliseError(response.status, null) };
      }
    }

    if (!response.ok) return { ok: false, error: normaliseError(response.status, parsed) };
    return { ok: true, data: parsed as T };

  } catch (err) {
    const aborted = err instanceof DOMException && err.name === 'AbortError';
    return { ok: false, error: aborted ? clientError('timeout', ...) : clientError('offline', ...) };
  } finally {
    clearTimeout(timer);
  }
}

That catch is the only one in the entire browser application. Every outcome — including the two nobody writes tests for, a proxy returning an HTML error page and a 200 whose body will not parse — comes back as a value describing what happened.

Reading the body as text first is the detail that makes the malformed cases distinguishable. Calling .json() directly would throw, and the throw would be caught by the outer handler and reported as a network failure, which is a different and misleading thing to tell someone.

The five-second timeout exists because a request that hangs produces neither an error to report nor a result to use. Nothing resolves, the "never blocks" guarantee quietly stops holding, and there is no symptom to notice.

challenges/ and ui/help/ — teaching, as data

Eleven challenge cards and eight help sections, all stored as plain data structures rather than as markup. That choice is what allows automated tests to check them: that every card's text placeholder names a real field, that every concept a card teaches has an explanatory note and vice versa, that every element the help text describes actually exists in the page.

07

The server — server/

One ASP.NET Core project in C#, about 500 lines. It shares no code with the browser — only the shape of the JSON that passes between them. It is entirely optional; the application works with it absent.

The lesson this layer taught, twice

Fakes prove endpoint behaviour and cannot prove persistence behaviour. Eleven endpoint tests passed while listing was broken in real SQL: SQLite cannot sort by the date type being used, and the in-memory fake sorted it happily. The server failed the first time it was started by hand.

And a database built fresh in a test cannot prove upgrade behaviour. A later change added a table; every test passed, because every test builds its database from scratch, while every request against the existing database failed. Both bugs have the same shape: the tests create the world as it should be, and reality arrives as it already is.

08

Five patterns that repeat

Once you have seen these five, most of the codebase stops holding surprises.

1 — Pass the evaluator in

The core cannot import the simulator. So anything in the core that needs to simulate takes a function that simulates as an argument:

// the genetic algorithm
stepGeneration(island, evaluate)

// the task suite
runSuite(morph, gait, evaluateGait)

Three things fall out of this. Tests can pass a synthetic evaluator and run the whole algorithm in milliseconds. The command-line tools and the browser both pass the real one, so there is exactly one implementation and it cannot drift into two. And the dependency arrow stays pointing the right way.

Injecting the evaluator, in full

// packages/evolution/src/tasks.ts — the core, which may not import the simulator

export type TaskEvaluator = (
  morph: Morphology,
  gait: GaitParams,
  opts: { seed: number; seconds: number; terrain?: TerrainSpec; impulses?: ... },
) => TrialResult;

export function runSuite(
  morph: Morphology,
  gait: GaitParams,
  evaluate: TaskEvaluator,                  // ← passed in, never imported
  tasks = TASKS,
  seeds = TASK_SEEDS,
): Map<string, TrialResult[]> {
  const byTask = new Map<string, TrialResult[]>();
  for (const task of tasks) {
    const body = taskMorphology(morph, task);   // Payload makes the torso heavier
    byTask.set(task.key, seeds.map((seed) => evaluate(body, gait, {
      seed,
      seconds: task.seconds,
      ...(task.terrain  ? { terrain:  task.terrain  } : {}),
      ...(task.impulses ? { impulses: task.impulses } : {}),
    })));
  }
  return byTask;
}
// and the two callers, in two completely different environments

// scripts/tasks.ts — a command-line tool, running under Node
const byTask = runSuite(morph, gait, evaluateGait);

// apps/web/src/workers/island.worker.ts — a Web Worker in a browser
const byTask = runSuite(message.morphology, message.gait, evaluateGait);

This is the pattern that makes the whole dependency direction work, shown end to end. The core describes what to run — six tasks, five seeds, this terrain, that impulse — and knows nothing about how a trial is performed. The caller supplies the doing.

The payoff is not theoretical. The command line and the browser run the suite through the same function, so the scorecard printed by npm run tasks and the one drawn in the panel cannot disagree. Before this existed they were two copies of the same loop.

2 — Configuration is data, not code

Tasks, challenge cards, help sections, goal presets, keyboard shortcuts — all arrays of plain objects. Data can be counted, cross-referenced and validated by a test; code branches cannot. When the task suite needed a metric per task, the design called for an expression language and it became a key into a lookup table instead: a parser and a sandbox to avoid a six-entry table is a bad trade.

3 — Generate, do not retype

The help section lists the keyboard shortcuts, and so does the toolbar hint strip, and so does the key handler. Those were three descriptions of the same thing, free to drift apart. Now there is one array; the handler dispatches from it, the hint strip is generated from it, the help renders it.

The same applies to help's glossary of tasks and goals — it renders the real TASKS and PRESETS, and tests assert identity rather than similarity, because a paraphrase is exactly the drift the arrangement exists to prevent.

4 — One rule, written once

The archive's "higher fitness wins, ties keep the incumbent" rule is used when an island inserts, when four islands are merged, and when a stored map is read back. All three go through the same function. A merge that resolved ties differently from an insert would make the displayed map disagree with the workers' maps in a way nobody would ever notice.

Where the rule genuinely has to exist twice — once in TypeScript, once in C# on the server — the response is a test that pins the tie direction, verified by deliberately reversing the comparison and watching the right test fail.

5 — Pure core, thin shell

Wherever something needs a browser, the part that needs it is separated from the part that does not. The 3D scene-building arithmetic is in a file that imports nothing from Three. The scorecard's formatting logic is separate from the DOM it eventually writes to. The help document's emphasis parser is separate from the elements it builds.

In each case the interesting half is testable in Node and the untestable half is a dozen lines of createElement.

09

How the tests are designed

314 tests in the browser project running in about one and a half seconds, and 30 on the server. The speed is not incidental — a suite that takes a second gets run before every change, and one that takes a minute does not.

Mutation testing, by hand

A test that has never failed has never been shown to work. Several times in this project a guard was verified by deliberately reintroducing the bug and confirming the right test — and only the right test — went red. Reversing the archive's tie comparison from >= to > fails the real-database test and leaves the fake-backed endpoint test green, which is itself the proof that fakes cannot carry that rule.

The rule about failing tests

Never loosen a test to make a change pass If a test fails, either the change is wrong or the change is deliberate. Say which, in the commit message, and update the expected value in the same commit. Three of the tests in this project are guards for bugs that actually shipped, and they are the cheapest insurance available.

10

Adding something new

Three worked routes through the layers, in increasing order of blast radius.

A new panel — the easy case

  1. Write a createXPanel(host, handlers) in ui/ that returns an object with methods for updating it. Keep the formatting logic in exported pure functions.
  2. Add a container <div id="x"> in index.html.
  3. Wire it in main.ts: create it, call its update method from the paint loop.
  4. Give its header an id and add a row to the help content so it gets a ?.

Nothing below apps/web changes. This is most new work.

A new task for the scorecard

  1. Add an entry to TASKS in evolution/tasks.ts — terrain, duration, metric, thresholds, and a sentence saying what failing it tells you.
  2. If it needs a new terrain shape, add a case to TerrainSpec and its height arithmetic, and a matching collider in sim/world.ts.
  3. Run npm run tasks -- --calibrate and set the thresholds from the table it prints, rather than from taste.
The rule that decides whether it is a real task A task whose own parameter barely moves its result is broken, not hard. Two of the eight originally specified tasks were cut by this rule — one because the physics has no sideways axis for it to exist in, and one because the ground representation cost more than the terrain did, measured at 1.70 m, 1.14 m and 1.15 m for zero, one and three centimetres of roughness.

A new gene — the expensive case

Adding a twelfth number to the genome touches the encoder, the decoder, the gene-range table, the slider panel, the URL format and the stepper's gene strips. More importantly it invalidates every stored gait and moves the golden number, because an eleven-number genome and a twelve-number genome are not comparable.

That is a deliberate cost. The genome is fixed at eleven because that keeps it comparable across bodies — you can evolve a gait, lengthen the robot's legs and watch it fall over, and the shared behaviour map can merge cells contributed by different people. Both properties depend on every genome meaning the same thing.

If you read nothing else

The core is pure arithmetic and cannot reach the physics engine or the screen. Anything that needs to simulate takes a function that simulates as an argument. Randomness is seeded and physics steps at a fixed rate, which together make runs reproducible. Reproducibility makes the golden test possible, and the golden test is what makes it safe to change anything at all.

Every other rule in this document exists to protect one of those four sentences.
