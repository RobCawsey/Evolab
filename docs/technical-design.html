Revision note — this one reverses a decision. Versions 1.0–1.4 were written for a funded team of four shipping a product with shared, reproducible, cloud-assisted runs. The centrepiece of that design was a Rust evolution kernel compiled to WebAssembly, so that the browser and a C# server would compute identical numbers. 01 — Thesis

One loop, four rooms

Evolab teaches two things by letting you do them: how a genetic algorithm searches, and what makes a walking gait work. It is a loop the user drives — build a body, evolve a gait for it, put the gait through trials, compare what came back — and the learning happens inside the loop rather than in a tutorial wrapped around it.

The audience is someone at the introduction-to-intermediate stage: comfortable with the idea that evolution optimises things, hazy on selection pressure, crossover, convergence and local optima, and with no vocabulary at all for duty factor or cost of transport. They are not being trained to ship a controller. They are being brought to the point where a fitness curve, a footfall diagram and a behaviour archive are things they can read.

That goal does not soften the architecture — it sharpens two requirements. Feedback has to be fast enough to be causal: if thirty generations take three minutes, nobody connects a change in the fitness function to a change in the outcome. And the algorithm has to be visible, not merely its results, because a learner who only ever sees a rising curve has learned that the computer figured it out. §7 sets out how; the rest of the document is what makes it possible.

The single hardest constraint is honesty about time. A genetic algorithm is a brute-force search: a hundred generations of a hundred individuals is ten thousand physics simulations. If the user has to watch each one render, the loop takes hours and the product dies. So the governing rule of this architecture is simulation is decoupled from rendering. Evolution runs headless, in parallel, off the main thread, as fast as the CPU allows. The 3D view replays recorded trajectories. Nothing the user looks at is ever waiting on physics.

The second constraint is that a GA is opaque. Users abandon optimisers they cannot read. So the interface is built around legibility of search: not just a fitness curve going up, but a behaviour archive showing what kinds of walking have been found, a lineage showing which mutation mattered, and side-by-side replay so improvement is something you watch rather than infer.

Room 01

Design

Assemble a biped from segments and joints. Set limits, motor torque, mass, sensors. Ships with three templates so nobody starts on a blank canvas.

Room 02

Evolve

Choose a controller and objective, launch the run. Watch fitness, diversity and the behaviour archive fill in live — and turn the cloud dial up mid-run when local cores aren't enough.

Room 03

Trial

Take a genome through eight standard tasks — terrain, slopes, obstacles, pushes — and get a scorecard rather than a single number.

Room 04

Compare

Replay candidates against each other, read the lineage back to the mutation that caused a jump, export or share the winner.

02 — System architecture

Four threads of execution

Everything that computes runs in the browser, in TypeScript, in Web Workers. The C# server stores things and shares things. That is the whole architecture, and its most important property is that one person can hold all of it in their head.

Reversing the kernel decision

v1.0 put the physics, the controller and the entire genetic algorithm into a Rust crate compiled to kernel.wasm, hosted by a Web Worker in the browser and by Wasmtime in .NET. The argument was sound: with a C# backend, a TypeScript GA would have to be reimplemented server-side and the two copies would need to agree bit-for-bit forever. One compiled artefact removed that duplication.

But look at what that requirement was for. Bit-identical cross-host results existed to serve the hybrid island ring — browser islands and cloud islands in one run, trading migrants, producing a result reproducible by anyone. That is a genuinely good feature for a funded product with many users. It is a feature that costs real money per hour and serves exactly one person here. Take the hybrid ring away and the reproducibility requirement it justified goes with it, and the kernel is left standing on nothing.

What it costs to keep is not small: a Rust crate, a WASM build pipeline, a hand-written FFI boundary marshalling flat buffers in two languages, Wasmtime hosting, and a cross-runtime hash suite in CI. It is also the slowest iteration loop in the stack and the least forgiving thing to build in conversation with an assistant — a category error away from a borrow-checker argument that has nothing to do with walking robots.

Decision, reversed. No Rust, no kernel, no Wasmtime. Physics comes from @dimforge/rapier2d and rapier3d — the same engine, already compiled to WASM and published as a JavaScript package, so the physics quality survives and only the toolchain ownership is given up. The GA, the controllers and the archive are plain TypeScript running beside it in the same worker. Deleted from the plan: one language, one build pipeline, one FFI boundary, one hosting runtime, one CI suite and the M0 gate.

Determinism survives in the form that actually matters day to day. A seeded RNG and a fixed timestep mean a run replays identically in the same browser, so a bug reproduces and a golden test is possible. What is given up is bit-identity across runtimes — a property that only had a customer in the feature just cut.

Thread 1

UI

React, Three.js, charts. Never blocks on physics, holds no simulation state. Everything the user looks at is reading a buffer.

Threads 2…N

Later

One ASP.NET Core project: stores runs, serves the SPA, mints share links. No evolution, no SignalR, no queue. Slice 12, and the app is complete without it — §5.

The island model stays, for a different reason

Islands were chosen because they map to worker cores: each is an independent sub-population evolving on its own schedule, trading a few elites with its neighbours every n generations, so no worker ever waits on the slowest trial in a batch. That reasoning is untouched by dropping the kernel — it is a property of having several cores, not of having a server.

It also survives on a second argument that matters more now: islands are the easiest parallelism to get right. Each one owns its own state, they communicate rarely and asynchronously, and a bug in migration degrades the search rather than corrupting it. For code written quickly and reviewed by one person, "wrong in a way that is obvious and survivable" is worth a great deal.

Decision. Island-model GA, one island per worker, ring migration of 2 elites every 5 generations — all in-browser. The hybrid ring, the cloud island lease and the Compute panel (Fig 9.6) are cut from the build and kept in this document as a design that the architecture still permits, should this ever have more than one user.

03 — Evolution kernel

What is actually evolving

The morphology is authored by the user and held fixed during a run. What the GA searches is the controller — the function mapping time and sensor state to joint targets. Three encodings are offered, in ascending order of power and descending order of interpretability.

EncodingGenomeGenesCharacterDefault for
ParametricPer-joint Fourier series over gait phase, 3 harmonics 6·J + 2 Open loop, perfectly periodic, and — decisively for teaching — every gene maps to a visible feature of a curve you can point at. Default
CPGCoupled Matsuoka oscillators, one per joint, plus feedback gains 9·J + 4 Rhythm emerges; sensory feedback modulates phase, so it recovers from small pushes. Second controller
NeuralMLP policy, sensors → torques, 2 hidden layers of 24 ~1.4k Most capable, least legible. Needs 5–10× the evaluations to converge. v1.1

J = actuated joint count; a default biped has J = 10 (hip pitch/roll, knee, ankle pitch/roll ×2), or J = 6 in the 2D sagittal mode that guided runs use.

Decision, changed for the teaching goal. Parametric is the default, not CPG. A 62-gene genome whose every value is a visible property of a curve — this harmonic controls that bump in the knee trace — is the difference between a learner reasoning about the search and watching a black box improve. CPG is the deliberate second step, offered once someone has asked why their gait cannot recover from a shove. Neural moves to v1.1: it is the least legible encoding and the slowest to converge, which is the wrong trade for this audience in v1.

Operators

  • Representation — real-valued vector in [0,1]ⁿ, decoded through per-gene ranges. Keeps every operator encoding-agnostic.
  • Selection — tournament, size 3, with 2 elites carried unchanged per island. Elitism is non-negotiable: without it the best gait can be lost to a bad seed.
  • Crossover — simulated binary crossover (SBX, η=15) at p=0.9. Blends rather than splices, which suits continuous control parameters.
  • Mutation — polynomial mutation with a self-adaptive per-genome σ, itself under selection. Late-run runs fine-tune instead of thrashing.
  • Multi-objective — NSGA-II when the user selects more than one objective. The UI then shows a Pareto front instead of a single champion, because "fastest" and "most efficient" are different robots and the user should get to choose.

Fitness, and how it gets cheated

Naïve distance-travelled fitness reliably produces a robot that dives forward and lands on its face at 4 m/s. The scoring function has to be defensive from day one:

Behaviour archive, not just a best score

A fitness curve tells you the search improved but not what it found. Evolab runs MAP-Elites alongside the GA: a 2D grid indexed by behavioural descriptors — typically stride length against duty factor — where each cell retains the fittest genome exhibiting that behaviour. The grid becomes the primary visualisation of a run. It shows coverage, dead zones, and the fact that the third-best genome is a completely different way of walking, which a leaderboard would have hidden.

Decision. Every run maintains a 24×24 elite archive. It costs one map insert per evaluation and gives the UI its most distinctive screen.

Determinism, scoped to what it is for

Reproducibility here buys two things, and neither of them is cross-machine byte equality. First, a bug reproduces — when a gait collapses at generation 63, it collapses at generation 63 again, which is the difference between debugging and guessing. Second, a golden test is possible: seed 4417 evolves to a known fitness sequence, and any change that perturbs it is caught by CI rather than by a vague sense that the robots look worse than they did last month.

Both follow from two rules with no infrastructure attached: a seeded xoshiro128** stream threaded explicitly through every stochastic call, and a fixed physics timestep. There is no Math.random() anywhere in the evolution module — that is a lint rule, not a convention.

Decision, narrowed. Determinism within a browser build, not across runtimes. The cross-runtime hash suite, the pinned WASM feature set and the recorded build hash all went with the kernel. A run manifest still records the Rapier version, because upgrading the physics engine will change results and that is worth knowing when an old run replays differently.

Module surface

Small enough to hold in your head, and every function pure. This is the entire evolution engine's public shape — plain TypeScript, no build step of its own, testable under Vitest without a browser.

04 — Simulation

Physics, and the budget it has to fit in

EngineDeliveryArticulationDeterminismVerdict
RapierRust → WASM, ~1.1 MBReduced-coordinate multibody joints Cross-platform deterministicSelected
Ammo / BulletC++ → asm.js/WASM, ~1.6 MBbtMultiBody, mature Platform-dependent FP pathsFallback
MuJoCo WASM~3 MB, heavier initBest-in-class contact model DeterministicPhase 2
BepuPhysics v2Native C#, SIMD, very fastExcellent solver, server-side only Deterministic — but not the same numbersRejected
Matter.js (2D)Pure JSRigid bodies + constraints DeterministicNot needed

Rapier wins on three counts: one engine serves both the 2D sagittal prototyping mode and the full 3D mode, it exposes reduced-coordinate joints so a biped is a proper articulation rather than a stack of constraint solves, and it is deterministic across platforms.

BepuPhysics is no longer a contender, and the reason is worth recording because it changed. In v1.0 it was rejected for producing different numbers from the browser's Rapier, which would have broken the hybrid ring. That argument is now moot — there is no server simulation to disagree with. It is simply not needed: physics happens in the browser, and a managed C# engine cannot run there.

Decision. @dimforge/rapier2d-compat and rapier3d-compat from npm — the same Rust engine, already compiled, versioned and published by its authors. Fixed timestep 1/240 s, 4 solver iterations, control resampled at 60 Hz, trials of 8 simulated seconds. The -compat builds inline the WASM as base64, which sidesteps an entire category of bundler and worker-loading problems — worth the slightly larger download on the first slice, and revisitable later.

Keeping the simulation testable

The kernel is gone but the discipline it enforced should not be. Rapier will happily be called from anywhere, and the failure mode of a quickly-built simulation is physics code entangled with rendering code such that nothing can be tested without a canvas.

  • One module, one entry point. evaluate(morphology, genome, task, seed) → FitnessResult is a pure function. It creates a world, steps it, returns numbers, and disposes. No DOM, no globals, no timers.
  • Recording is a flag, not a mode. The same function optionally returns a trajectory buffer. There is never a second code path that simulates "for display".
  • The RNG is a parameter. Never Math.random(), anywhere, for anything. A seeded generator is threaded through explicitly, which is what makes the golden test below possible.
  • It runs in Node. Because it touches nothing browser-specific, the whole evolution loop runs under Vitest — so a regression is caught by a test rather than by noticing that the robots look worse.
Decision. One golden test from the first slice that evolves a fixed seed for 20 generations and asserts the exact fitness sequence. It costs ten minutes to write, runs in under a second, and is the only thing standing between a working GA and six weeks of "it used to walk better than this".

Full run archive~4 MBChampion + archive elites only, 200 gens

Only champions and archive elites keep their trajectories; the other 99% of evaluations return a fitness vector and nothing else. That single rule is what keeps a long run inside a few megabytes instead of a few gigabytes, it is why the replay view can scrub instantly, and it is also what keeps the hub quiet — a generation costs about six kilobytes on the wire, so the network is nowhere near being the constraint.

The first three rows are the ones the teaching goal turns on. A 2D sagittal biped with six joints over a four-second trial is roughly fifty times cheaper than the full 3D benchmark configuration, which puts an entire thirty-generation search inside a second and a half. That is the difference between evolution as something you launch and come back to, and evolution as something you watch — and it is what lets a learner change one weight in the fitness function and see the consequence immediately. No new machinery: the same code, a smaller job.

These numbers did not change when the kernel was dropped, because the physics is the same compiled Rapier either way — only the ownership of the build changed. What was given up is the ability to buy throughput with cores. On a desktop that means five minutes for the longest run in the product, which is a fair price for deleting a language from the stack.

05 — .NET services

What the server is responsible for

One project, about ten endpoints, a SQLite file. The server exists so that runs outlive one browser profile and so that a gait can be shown to somebody — and for a long while it will not exist at all, because slices 0 to 11 do not need it.

This is a deliberate demotion. v1.0 specified three deployables, a queue, a Wasmtime pool, a SignalR hub, leases, quotas and autoscaling, all of which followed from running evolution on the server. Evolution no longer leaves the browser, so all of it goes. What remains is a conventional CRUD service, which is a considerably better thing to build in the evenings.

Warning worth stating plainly. A C# developer will want to start here. It is the familiar ground, the part where the shape of the work is obvious, and there is a real temptation to spend the first three weekends on a well-layered API for a client that does not exist yet. Everything valuable about Evolab happens in the browser. The server is slice 12 for a reason, and the reason is discipline rather than architecture.

  • SQLite, and probably forever. One writer, a few thousand rows, a few hundred megabytes at the extreme. Postgres would be ceremony. EF Core keeps the option open for the price of a connection string.
  • Trajectories as files. Content-addressed by hash under a data directory. A blob store abstraction can wait until there is a second machine.
  • Auth last, and minimal. Until publishing exists there is nobody to authenticate. When it does: one provider via OIDC, no password handling, no registration form to build or defend.
  • No SignalR. It was there to stream generations from cloud islands. There are no cloud islands. If a live shared view is ever wanted, add it then.
  • Deploys as one container or one dotnet publish to a cheap VPS. There is no orchestration story because there is nothing to orchestrate.
Decision. Evolab.Server — a single ASP.NET Core project with EF Core, SQLite and static file hosting, serving the SPA it stores runs for. Roughly three sessions of work, and none of them before slice 12.

06 — Task suite

Eight ways to fail

Gaits evolved on flat ground are brittle in a way that is invisible until you test them. The trial suite exists to expose that: a genome is scored per task, and the scorecard — not the training fitness — is the artefact the user shares.

TaskSetupPrimary metricTests
Sprint20 m flat, 15 s limitMean forward velocityRaw speed
Endurance200 m flat, no limitCost of transportEfficiency, limit cycle stability
RoughPerlin heightfield, ±4 cmDistance before fallFoot placement tolerance
InclineRamps −12° to +18°Summit timeTorque headroom, pitch control
StepsFour 12 cm risersSteps clearedSwing-height adaptation
SlalomSix waypoint gatesPath efficiencySteering, turn-in-place
ShoveLateral impulses, 40–120 N·sRecovery rateClosed-loop reflex quality
Payload+25% torso massVelocity retainedRobustness to model change

Each task runs across k = 5 seeds and reports median with spread, because a gait that clears the steps once in five is a gait that does not clear the steps. The composite badge — bronze, silver, gold — requires a minimum score in every task, so a sprint specialist cannot buy a gold with speed alone.

Decision. Tasks are declarative JSON — terrain generator, spawn, success predicate, metric expression. They load as data, so new tasks ship without a release and users can author their own in v1.1.

07 — Learning design

Teaching by instrument, not by tutorial

The temptation with an educational build is to wrap the real application in a layer of explanation — a tour, some tooltips, a glossary — and call it taught. That produces someone who can operate Evolab and still cannot say what selection pressure is. The approach here is the opposite: the same instrument throughout, revealed in stages, with the algorithm itself made into something you can watch step by step.

Guided is not a demo or a sandbox — it writes to the same run records, and a study begun there can be opened in Lab without conversion. The stages differ in what is shown, not in what is real.

Decision. Stages are freely switchable from the toolbar at any time, and the challenge track only suggests progression. Nothing is locked. A postgraduate who arrives already knowing NSGA-II should reach the full instrument in one click, and a beginner should never be punished for looking.

Making the algorithm visible

This is the central design move and the one new screen the teaching goal earns: a generation stepper that halts the search between operators and shows each one acting on actual genomes. Population, evaluation, tournament, crossover, mutation, replacement — six stages, steppable, with the genes drawn as coloured strips so a crossover is visibly two parents becoming a child and a mutation is visibly three values moving.

It matters because the alternative teaches the wrong lesson. A learner who only sees a rising fitness curve concludes that the computer solved it. A learner who watches a tournament discard two of three candidates, and then sees the survivor's genes spliced and nudged, has understood selection pressure without being told a definition. Fig 9.4 is that screen.

The stepper is not a simulation of the algorithm for illustration. It is the real kernel, paused between calls, reading real genomes out of the real population — which is why it can be left available in Explorer and Lab rather than being a beginner's toy.

The best lesson is the one we listed as a risk

§15 records reward hacking as a high-likelihood risk: naïve distance-travelled fitness evolves a robot that dives forward and lands on its face. For a product that teaches, that behaviour stops being a defect and becomes the single most valuable thing in the curriculum.

So it is staged deliberately. An early challenge — "Get it 10 metres from the start" — ships with exactly the naïve objective. The learner watches their robot launch itself down the track, score brilliantly, and be obviously wrong. Then they are asked to fix the objective, not the robot. That single exercise teaches specification gaming, the gap between a proxy and an intent, and why every term in Fig 3.1 exists — and it teaches it as something the learner discovered rather than something they were warned about.

Decision. The defensive fitness terms from §3 are off in the first fitness-design challenge and switched on by the learner, one at a time, as they diagnose each failure. Everywhere else they default on.

Explanations that cannot rot

  • One affordance, everywhere. A single ? control on any panel opens a short plain-language note in the right rail. No tooltips, no modals, no tour that hijacks the pointer.
  • Written against live values. Notes interpolate the run's actual numbers — "your diversity has fallen to 0.31, which is why the last 20 generations barely moved" — so they read as observations rather than documentation.
  • Authored as data, verified in CI. Notes live in the same JSON layer as task definitions (§6), keyed to concept ids. A test asserts that every concept referenced by a challenge has a note and every note is reachable, so the explanation layer cannot silently drift from the product.
  • Dismissible for good. Turning explanations off in Lab is permanent per concept, not per session. Being re-taught something you know is the fastest way to lose an intermediate user.

08 — Interface system

An instrument, not a document

Evolab is scanned and operated rather than read. The interface is built as a fixed instrument chassis — toolbar, mode rail, three columns, transport bar — whose middle stage swaps per room while the surrounding controls stay put. Users learn one layout once.

  • The chassis never changes, only what is mounted in it. Guided, Explorer and Lab (§7) are the same toolbar, rail and columns with fewer panels present — not three layouts. Progressing is additive, so nothing a learner knows becomes wrong.
  • State reads as form, not just number. Running, converged, stalled and failed each have a distinct chip and colour, so a run's health is legible from across a desk.
  • Amber means champion. One accent, one meaning, everywhere: the current best genome. Population series are slate-cyan, archive elites violet, pass/fail jade and rust. No decorative colour anywhere in the product.
  • Every chart is scrubable and linked. Clicking generation 41 on the fitness curve selects that generation across the archive, the population grid and the replay.
  • Dark by default. Long sessions staring at a 3D stage; a light theme ships but the product's identity is the dark instrument skin shown here.

Rendering strategy

3D stage

Three.js / R3F

Instanced meshes for ghost replays, a single draw call per robot. LOD drops to capsule proxies beyond 12 m. Frame-rate capped at display refresh, paused when the tab is hidden.

2D analysis

Canvas 2D + uPlot

Gait diagrams, phase portraits and joint traces. uPlot handles the streaming fitness chart at 60 Hz with tens of thousands of points where SVG would collapse.

Archive grid

Canvas, one bitmap

576 elite cells repaint as a single ImageData blit rather than 576 DOM nodes, so live archive updates cost nothing.

10 — Responsive strategy

Degrade the chassis, keep the instrument

A three-column workbench does not fold into a phone. Rather than reflowing it, Evolab changes what the device is for: desktop authors and evolves, tablet reviews, phone monitors. The data layer is identical; the affordances are not.

BreakpointChassisEvolutionEditing
≥ 1280 pxRail + 3 columns + transportFull local poolFull authoring
900–1279 pxSide panels become overlay drawersFull local poolFull authoring
600–899 pxStage + bottom sheet, tabbed analysisPool capped at 4 workersInspect & tune only
< 600 pxSingle column, monitor modeRemote run onlyRead-only

Two hard rules keep small devices honest. The worker pool never exceeds min(hardwareConcurrency − 1, 4) on touch devices, because a thermally throttled phone that has locked up is a broken app regardless of who is at fault. And running a local evolution requires an explicit opt-in on battery power, with an estimated completion time shown before the user commits.

Decision. Mobile is a first-class monitoring client, not a cut-down editor. It gets push-quality live run state, the scorecard and replay — and does not pretend to offer morphology authoring on a 390 px canvas.

11 — Data & sync

What gets stored, and where

IndexedDB (Dexie)

Structured records

Projects, morphologies, run and generation metadata, genomes. Indexed on runId and genomeHash.

OPFS

Trajectory blobs

Quantised binary buffers, one file per recorded trial. Written from the persistence worker, read as ArrayBuffer straight into the replay.

PostgreSQL + EF Core

Server of record

The same entity model, append-only. Generations partitioned by runId; genomes stored as bytea keyed on content hash and shared across every run that produced them.

Blob store

Server trajectories

Content-addressed, immutable, served through a CDN. Identical bytes to the OPFS copy, because the same kernel produced them.

.evolab bundle

Portable export

Zip of manifest.json + genomes + selected trajectories, carrying the kernel build hash so an import can say honestly whether it can reproduce the run.

Sync needs no CRDT, and that is not an accident

Two writers — a browser and a server — editing one run is normally where a design like this acquires a conflict-resolution layer nobody enjoys maintaining. It does not here, because of a property the domain already has: a computed generation is immutable. Generation 41 of island 7 is a fact produced by a pure function of (genome, morphology, task, seed). It is never edited, never recalculated, never superseded. Islands own disjoint index ranges, so two hosts cannot even write the same key.

Sync therefore reduces to set union over an append-only log, keyed on (runId, islandId, generation). Reconnect after an hour offline and the client sends its highest cursor per island, the server sends everything above it, and both sides converge with no merge and no ambiguity. Redelivery is harmless because applying the same generation twice is a no-op.

Decision. Append-only, content-addressed, island-partitioned. The only genuinely mutable records in the system are project name, objective weights and lease state — all last-writer-wins, all trivial.

Morphology immutability serves the same end and prevents the worst class of bug in this product: a user tweaks a knee limit mid-run and every prior generation's fitness silently becomes meaningless. Editing a referenced morphology forks a revision and offers to branch the run.

13 — Build plan

Slices, not milestones

A 32-week plan for four engineers was the wrong artefact. What one person building conversationally needs is a sequence of slices, each finishable in a sitting or two, each ending with something that runs. The measure is not percentage complete — it is whether the thing on screen is more interesting than it was last weekend.

The first four slices are the spine. They take roughly six sessions and end with a genetic algorithm evolving a gait while you watch a fitness curve climb. That moment is the entire project in miniature: if it arrives, momentum takes care of itself, and if it does not arrive the rest of this document is moot. Everything after slice 3 is enrichment, and every slice after it can be skipped or reordered without breaking what came before.

Rule. The app runs at the end of every slice. No slice leaves the tree broken overnight, and no slice is "the refactor one". If a slice cannot be finished in two sittings it was too big and should be split before it is started.

Working this way with an assistant

Building conversationally is fast at producing plausible code and poor at noticing that plausible code is wrong. These are the practices that address that specifically, rather than general good hygiene.

  • The golden test is the whole safety net. With no second pair of human eyes, a seeded run asserting an exact fitness sequence is what catches a subtly broken crossover. Write it in slice 2, the moment there is a GA to test. A change that alters it is either a bug or a deliberate act — and being forced to say which, every time, is the point.
  • Make the compiler the reviewer. TypeScript strict plus noUncheckedIndexedAccess, C# nullable enabled, warnings as errors. Generated code fails these checks far more often than hand-written code does, which is exactly why they earn their keep here.
  • One concern per session. Physics tuning and UI work in the same sitting produces two half-finished things and a diff nobody can review. Dropping Rust helps enormously — there is now one language for everything that computes.
  • Keep the numeric core pure. §3 and §4 both insist on this and it matters most here: code with no DOM, no globals and no randomness can be verified in a test loop that takes a second, and that loop is what makes conversational iteration safe.
  • Commit per slice, with the run that proves it. A screenshot or a golden fitness number in the commit message. Six months on, this is what tells you whether a regression is recent.
  • Keep a CLAUDE.md of invariants. Fixed timestep, seeded RNG only, no physics on the UI thread, evolution module stays browser-agnostic. Written down, these survive between sessions; held in your head, they do not.
  • Distrust confident refactors. The most dangerous suggestion is a tidy rewrite of working simulation code. If the golden test still passes it is probably fine; if there is no golden test yet, decline.

Honest expectations

Thirty-three sessions is not thirty-three weekends. Slices 5, 7, 9 and 14 will each take longer than estimated — the morphology editor because editors always do, the 3D stage because getting a replay to look right is fiddly, and the task suite because eight terrain generators is simply a lot of small work. Against that, slices 0 to 3 will likely go faster than written, because Rapier's examples do most of the hard part and there is no UI to speak of yet.

At one or two sessions a week, the spine lands inside a month and the full scope is most of a year of evenings. The right way to read the table is not as a schedule but as a permission structure: everything below slice 11 is optional, and a version of Evolab that stops at slice 8 is a finished thing rather than an abandoned one.

14 — Environment

One machine, two commands

The four deployment profiles of v1.4 collapse into one. There is a dev server and, from slice 12, a .NET project that serves the built frontend. No containers, no orchestration, no Postgres, no Aspire — all of which existed to manage a topology that no longer exists.

Repository shape

A plain npm workspace with one .NET project beside it. Deliberately not a monorepo with tooling — the boundary that matters is the one between numeric code and everything else, and a workspace package is enough to enforce it.

What a desktop needs

Nothing unusual: Node 22 and a current browser for slices 0–11, plus .NET 10 from slice 12. Cores are the only spec that affects the experience — evolution throughput is linear in them — and an 8-core machine runs the full 3D benchmark configuration in about two minutes, with the guided 2D runs finishing faster than you can look away. WebGL2 for the 3D stage; integrated graphics are fine, because the scene is a dozen capsules.

Decision. No Docker anywhere in the project, including for the database. If a dependency needs a container to run locally, that is evidence it does not belong in a personal project of this size.

15 — Classroom

What a teacher view actually costs

A teacher view is not a dashboard with a class filter on it. It is the point where Evolab stops being a single-player tool and becomes a system holding identifiable records about other people's children. The screen is the cheap part; the substrate underneath it is the work.

Correcting an earlier estimate. §16 previously costed this at about three weeks. That was wrong, and wrong in a way worth naming: I was pricing the cohort dashboard and silently assuming the identity, authorisation and data-protection layers it sits on already existed. They do not. The honest figure is roughly seventeen person-weeks for the full capability — but most of that buys things a first version does not need, which is what the phasing below is for.

The thing that makes this expensive

Every other feature in this document manipulates numbers: genomes, trajectories, fitness vectors. None of it is personal data and none of it carries obligations. A class roster is different. The moment the server stores "Ada K. is in Year 10 Computing and is stuck on challenge 3", Evolab is processing personal data about a minor, and inherits retention limits, deletion rights, parental-consent questions, subject-access obligations, and a duty to be defensible about all of it.

That is not a reason to avoid the feature. It is a reason to design the data footprint before the dashboard, because retrofitting privacy onto a schema that already assumed named students is the expensive path.

Decision. Pseudonymous by construction. The server stores a per-class opaque handle and progress against it — never a real name, never an email, never free text. The handle-to-name mapping lives in the teacher's own browser, exported and imported as a file they control. The teacher sees a class list; the database never contains one.

This is not a trick to dodge obligations — the data is still personal while the teacher holds the key — but it collapses the blast radius. A breach of Evolab's database yields quiet-heron completed challenge 4. It also makes deletion trivial and makes the self-hosted deployment in §14 a genuinely strong answer for a school: run Evolab.Host on a classroom PC and no student data leaves the building at all.

Phase A gets most of the value for a third of the cost, and it does so by exploiting something already true: the client is local-first. A student's work already lives in their own browser. Joining a class does not move it — it starts pushing summaries (which challenge, how many attempts, best fitness, concept progress) to the server under a pseudonym, with genomes and trajectories following only when they submit. No student accounts, no passwords to reset in a lesson, no parental consent workflow, no minor's PII in the database. A teacher creates a class, reads out a six-character code, and thirty browsers appear on the dashboard.

Recommendation, revised. There is no classroom behind this yet — it is a hypothesis. So Phase A is specified and not scheduled. Building a cohort dashboard for an imagined teacher produces the thing this section warns about: metrics that are easy to compute, a gradebook nobody asked for, and four weeks spent on the one feature that carries legal obligations. The design above is the deliverable; the code is not, until a real teacher and a real class exist to build it against.

That is not a soft no. It is worth having designed, because knowing how it would be built tells us which cheap decisions to make now — and those are the ones that matter.

Equally, what not to do now: no roles or permissions UI, no student accounts, no assignment builder, no consent or retention machinery. Each of those is only correct in the presence of a real school, and each is expensive to carry while being wrong.

The one part worth taking now

The best idea in this section is not the dashboard — it is the class archive: thirty people's elites merged into one grid, showing that the room found six genuinely different ways of walking. That is the quality–diversity lesson delivered better than any explanation of it.

And it has nothing to do with classrooms. Decoupled from a cohort it becomes a community archive: anyone who publishes a run contributes their elites to a shared grid, and every learner sees the space of solutions found by everyone before them. Same lesson, larger sample, and none of the cost — no roster, no accounts, no minors, no obligations, because a genome is a list of numbers and carries no personal data at all.

Decision. The community archive is the classroom feature worth building without a classroom. It reuses the archive merge that already exists as island migration (§2), needs only the share mechanism already specified in §5, and gives the diversity lesson to a solo learner — who, as things stand, is the only user this product actually has.

What a teacher needs, and what falls out for free

The concept ladder in §7 was built to sequence a learner's encounters. It turns out to be a gradebook. Per-concept mastery already exists per student, so a cohort view is that same structure with a second axis — no new tracking, no new instrumentation, no telemetry added to the client for this.

  • Where the class is stuck. Completion per challenge across the cohort, which immediately shows the wall — usually challenge 3, by design.
  • Who needs help right now. Attempts without a pass, time on a challenge well beyond the cohort median, or a run whose diversity has collapsed. Surfaced as a short list, not a score.
  • Misconception signals. The one worth building deliberately: students who passed the ten-metre challenge without editing the objective have gamed it rather than learned from it, and that is detectable exactly. It is the difference between a dashboard and a teaching instrument.
  • The class archive. Aggregate every student's elites into one MAP-Elites grid. A teacher can then show the room that thirty people found six genuinely different ways of walking — which is the quality-diversity lesson delivered better than any explanation of it. This is close to free: the archive merge already exists as island migration.
  • Live session view. Who is running what, right now. The SignalR hub already broadcasts generation summaries; a class-scoped group is a small extension.

The deployment schools will actually want

§14's desktop profile turns out to be the classroom answer, and it needs no new work. A teacher runs Evolab.Host on one classroom PC; thirty students connect over the LAN; the browser does each student's evolution on their own machine, so the teacher's PC is only serving progress records. No internet dependency, no cloud bill, no data leaving the site, nothing for a school's IT department to procure or approve.

Decision. P1 is the reference classroom deployment and the documentation leads with it. The hosted service is for individuals and for schools that would rather not run anything. This also means the privacy conversation with a school can start with "it does not have to send us anything", which is a materially easier conversation.

Open questions, and what I have assumed

  • Answered: the smallest version worth building. This was the standing question and the answer is slices 0–3 — a working GA evolving a visible gait in roughly six sessions, no backend, no accounts, no cloud. §13 is built around it.
  • Closed: who pays for compute. Nobody. Cloud evolution is cut, so there is no bill, no quota UI and no abuse surface to design.
  • Morphology evolution. The body is fixed and only the controller evolves. Co-evolving both is a larger search and a different UI — and, unusually for a deferred feature, it is also the most interesting thing this project could grow into. Worth a v2, not a v1.
  • Fidelity ceiling. Plausible-looking locomotion, or gaits that would transfer to hardware? I have assumed the former throughout. The latter pulls in MuJoCo, actuator models and domain randomisation, and would roughly double the project.
  • Does anyone else ever use it? Slices 12 and 13 assume yes, at least a little — publishing runs, a community archive. If Evolab stays entirely personal, both can be dropped and the project ends at slice 14 with no server at all. That is a legitimate ending and worth deciding before slice 12 rather than during it.
Recommendation. Start at slice 0 this week. It is a Vite project, Rapier from npm, a canvas, and a biped that falls over — an evening's work with no architectural decisions left to make, because they are all in this document. Then slice 1, then slice 2 with its golden test, and by slice 3 there is a genetic algorithm evolving a gait in front of you. Everything else in these sixteen sections is what to build after the project has proven it is worth continuing.

The one thing I would add before slice 0 is CLAUDE.md at the repository root, carrying the invariants from §13: fixed timestep, seeded RNG only, no Math.random in packages/evolution, nothing browser-specific below apps/web, and the golden test is never deleted to make a change pass. Those four lines are what keeps twenty sessions of conversational building pointed in the same direction.
